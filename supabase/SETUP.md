## Что требуется от владельца

1. Войти в Supabase и выбрать или создать отдельный проект для тетради.
2. Применить `migrations/202609280001_intro_workbooks.sql` через SQL Editor либо Supabase CLI. Миграция создаёт только новые объекты тетради.
3. В Authentication → URL Configuration указать Site URL и разрешённый redirect URL: `https://glebastashev.github.io/ai-engineer-workbook/`.
4. Включить вход Email + Password, подтверждение почты и пароль минимум 12 символов. Настроить собственный SMTP для писем подтверждения и восстановления: встроенная тестовая отправка Supabase ограничена адресами команды проекта и не подходит для учеников.
5. В `.env.local` указать только адрес проекта и публичный publishable/anon key (пример ниже). Secret/service_role ключи не нужны в клиенте и не должны попадать в GitHub.
6. Проверить регистрацию, письмо подтверждения, повторный вход после очистки браузера, восстановление пароля и разделение двух реальных аккаунтов.
7. Выполнить `npm test`, `npm run build:cloud`, затем опубликовать исходники и `docs/` в `main`. Проверить GitHub Pages на реальном адресе.

```env
VITE_SUPABASE_URL=https://PROJECT_REF.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=PUBLIC_PUBLISHABLE_KEY
```

## Хранение и доступ

`intro_workbooks.user_id` связан с Supabase Auth. Правила RLS разрешают пользователю читать и изменять только свою активную запись. Отображение «Сохранено в аккаунте» появляется только после успешного ответа сервера. При временном сбое черновик остаётся в браузере отдельно для каждого аккаунта. Черновик, который ещё не дошёл до сервера, не переживёт очистку браузера; страница показывает для него ошибку сохранения.

Для закрытия доступа администратор меняет `active` на `false` у конкретной строки в Table Editor. Ответы не удаляются. Возврат `active=true` открывает прежние записи. Клиенту запрещено самому менять этот признак, владельца строки или удалять тетради. Удаление самого пользователя в Supabase Auth удаляет связанную тетрадь; для временного закрытия доступа пользователя удалять не нужно.

Локальные ответы прежней версии переносятся по кнопке после входа. Уже заполненные поля аккаунта сохраняются. Исходные локальные ответы при переносе не стираются; повторное предложение скрывается только после успешного сохранения.

## Что проверено локально

- SQL и RLS исполняются в PostgreSQL/PGlite: права, изоляция аккаунтов, запрет удаления, сохранение при закрытии доступа.
- Контроллер синхронизации: повторное открытие без локального хранилища, неудачный запрос и повторная отправка, правки во время сохранения, смена аккаунта.
- Браузер с тестовым API: форма входа, восстановление после очистки браузера, импорт прежних ответов, мобильная версия. Форма входа также проверена со сборкой, подключённой к реальному проекту; полная проверка с настоящими аккаунтами ждёт SMTP.

Официальные справки: [SMTP](https://supabase.com/docs/guides/auth/auth-smtp), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [пароли и восстановление](https://supabase.com/docs/guides/auth/passwords).
